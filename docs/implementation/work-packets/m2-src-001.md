## Goal

Let the authenticated owner add a Pasted Text Source to an active Content Package, preserve the original bytes as one immutable private Raw Snapshot, review a revision-controlled Normalized Source Working Copy, create immutable Normalized Source Versions, and explicitly approve one exact Version as the only future Research-eligible input.

## Implementation Requirements

1. Add framework-independent Source values, invariants, Ports, and application use cases in Core. Keep Domain code free of NestJS, Drizzle, S3 SDK, and transport types.
2. Model stable Source Reference identity, immutable Raw Snapshot metadata, one revision-controlled Working Copy, immutable Versions, distinct Head pointers, and append-only Approval records. Do not use one mutable current-Version flag or one universal JSON row.
3. Accept only `pasted_text`; accept roles `primary` and `supporting`; enforce one Primary and at most five Supporting Sources per Package.
4. Bound text by UTF-8 byte length, reject empty/whitespace-only or invalid input, and preserve the exact original bytes separately from the reviewed normalized body. Select and document the numeric bound as a reversible implementation detail.
5. Define a minimal Core-owned ObjectStore Port. Implement it in the new S3-compatible adapter with opaque, owner/Package/Source/Snapshot-scoped keys, immutable-put semantics where supported, SHA-256 verification metadata, and deletion used only to compensate a failed initial database creation.
6. Configure endpoint, region, bucket, path-style mode where needed locally, access key, and secret key through typed fail-fast API configuration. Secret values stay in `ApiSecrets`, never public config or logs.
7. Add one additive forward migration with relational constraints and indexes for owner/package lookup, role limits, revisions, version uniqueness, immutable identity, heads, and Approval uniqueness. Use explicit transactions for head and Approval changes.
8. Add protected REST contracts under `/v1/content-packages/:packageId/sources`. Keep Query, Working Copy edit, Version creation, and Approval as explicit operations. Map failures into the existing stable error envelope.
9. Use JSON Schema 2020-12 plus Ajv for the persisted Normalized Source Version body. TypeScript boundary types and the schema must have an executable synchronization or validation test.
10. Return safe Source metadata and normalized review content only where the endpoint explicitly requires it. Never return credentials, Snapshot object keys, temporary URLs, or raw object-store responses.
11. Extend the isolated smoke environment so tests use a fresh bucket/object namespace, never the `contentos-local` named volumes or permanent bucket data, and always remove temporary objects/buckets on success and failure.
12. Synchronize Current Truth without claiming file upload, URL Fetcher, Workflow, Queue, SSE, UI, Research, or Agent behavior exists.

## Acceptance Criteria

1. Valid owner-scoped Pasted Text capture creates one Source Reference, one immutable Raw Snapshot Object Reference, and one Normalized Working Copy for an active Package.
2. The stored bytes' SHA-256 and byte size match PostgreSQL metadata, and no existing Snapshot can be overwritten through public or application interfaces.
3. The owner can list and query Source review state without receiving storage credentials, object key, temporary URL, or unintended raw evidence.
4. Working Copy edits require `expectedRevision`; stale edits return a stable `409` and do not change stored state.
5. Explicit Version creation is immutable and records sequential number, optional parent, content hash, schema version, creator/time, and exact Snapshot dependency. Later edits cannot mutate it.
6. Explicit human Approval binds one exact eligible Version, creates one append-only Approval, and transactionally updates only the Approved head. Repeating the same command cannot create a duplicate Approval.
7. An Approved head is the only representation of future Research eligibility; no Research or Agent execution exists.
8. Second Primary, sixth Supporting, archived Package, invalid role/type/text, missing Session, owner mismatch, unknown Package/Source, stale revision, and ineligible/unknown Version fail closed with stable errors and without forbidden side effects.
9. A failed object write creates no database Source state. A failed database creation after object write attempts scoped compensation; cleanup failure is surfaced and never reported as success.
10. Missing/invalid storage configuration fails before the API accepts work and emits no Secret value.
11. Unit, schema, repository/migration, object-storage integration, protected API integration, regression, failure-injection, cleanup, Secret, local-path, and dependency checks pass.
12. Documentation reports `M2: In Progress` and `M2-SRC-001: In Review` only after implementation evidence is complete. M3 remains not started.

## Security Requirements

- Pasted Text and all Source bodies remain private and untrusted.
- Validate at the HTTP boundary and enforce the same invariant in Domain code.
- Parameterized Drizzle queries only; no user-controlled object key or filesystem path.
- Session plus owner authorization on every route; opaque IDs never substitute for authorization.
- No Source body, credential, object-store response, signed URL, full request, or object key in ordinary logs or errors.
- Private bucket/object access only. No public ACL and no browser-direct object fetch.
- Raw Snapshot and normalized review representation remain distinct.
- Approval is human-only, exact-Version-bound, append-only, and cannot be inferred from successful capture or version creation.
