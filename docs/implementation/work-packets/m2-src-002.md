## Goal

Let the authenticated owner capture a `.md` or `.txt` file upload as a Source of an active Content Package through one protected multipart route. The upload passes a request-scoped Upload Quarantine gate (allowlist, filename, declared-MIME, size, encoding, and content validation before any side effect). On success the exact original file bytes become one immutable private Raw Snapshot, a revision-controlled Normalized Source Working Copy is seeded from the validated UTF-8 text, and the existing immutable Version and human Approval foundation applies unchanged.

## Bounded Implementation Decisions (reversible implementation details)

1. **Upload size bound:** `UPLOAD_FILE_MAX_BYTES = 100_000` raw file bytes — equal to the documented `PASTED_TEXT_MAX_BYTES` bound and inside the existing `source_raw_snapshots_byte_size_check` (1..100000), so no snapshot size constraint change is needed. The decoded normalized text additionally satisfies the existing ≤100,000-byte normalized bound. Both bounds are documented in `source-foundation.md`.
2. **Taxonomy:** `sourceType = captureType = 'uploaded_text'` for this capture path, parallel to the `pasted_text` single-value precedent; matches the data-classification "Uploaded Text" vocabulary and DEC-268's input-path framing. The `.md` vs `.txt` distinction is carried by the Raw Snapshot content type.
3. **Stored Raw Snapshot content types (allowlist):** `.txt` → `text/plain; charset=utf-8`; `.md` → `text/markdown; charset=utf-8`. The `source_raw_snapshots_content_type_check` constraint and Core snapshot validation accept exactly these two literals.
4. **Declared upload MIME consistency:** accepted declared Content-Type values for either extension are `text/plain`, `text/markdown`, `application/octet-stream`, or absent/empty (browsers commonly send octet-stream for `.md`); any other declared type is a quarantine denial.
5. **Encoding validation:** strict UTF-8 decode (invalid sequences denied); one leading U+FEFF BOM is stripped from the normalized text only (the Raw Snapshot preserves the exact original bytes); NUL bytes and lone UTF-16 surrogates denied; decoded text must be non-empty after trim.
6. **Filename safety:** 1–255 bytes, no path separators (`/`, `\`), no NUL or C0/C1 control characters, final extension (case-insensitive) must be `.md` or `.txt`. Filenames never define filesystem paths (the whole flow is in-memory). When no label is supplied, the sanitized filename stem (extension removed, then the existing label rules: well-formed Unicode, ≤200 scalar values) becomes the Source label. The raw filename itself is not persisted in this slice (documented limitation).
7. **Quarantine model:** request-scoped quarantine. Uploaded bytes are held in a bounded request buffer and fully validated before any Object Storage or DB write; a denied upload creates zero persisted state (lifecycle cleanup is trivial: buffer release). This satisfies DEC-208 and Security Baseline §9 observable requirements for the synchronous MVP path: allowlist, validation-gates-object-creation ordering, isolation (no Source object before success), no execution, no trusted filename paths, formal failure, and no downstream reachability of unvalidated content. A persistent object-store quarantine for asynchronous flows/scanning remains an open future item (see Limitations).
8. **Multipart handling dependency:** `@fastify/multipart` (official Fastify plugin, Fastify v5 compatible) pinned to an exact verified version in `apps/api/package.json`. Justification: the approved stack is NestJS + Fastify; hand-rolled multipart parsing is a security liability; the plugin provides bounded `fileSize`/`files`/`fields` limits and is audited on the official registry. This follows the M2-SRC-001 bounded-choice precedent (`@aws-sdk/client-s3`). The lockfile delta must be limited to this plugin's tree.
9. **Route and error mapping:** new route `POST /v1/content-packages/:packageId/sources/upload` consuming `multipart/form-data` with parts `file` (exactly one), `role` (required), `label` (optional). Success returns the existing `SourceResponse` (201). All quarantine denials return `422 INVALID_REQUEST` with stable `details[].keyword` values: `upload-file-missing`, `upload-too-many-files`, `upload-file-size`, `upload-file-extension`, `upload-file-name`, `upload-media-type`, `upload-encoding`, `upload-file-empty`, `upload-field-invalid`, `upload-field-limit`. No new API error codes are added. Internal object/DB failures reuse the existing `SOURCE_CAPTURE_FAILED` / `SOURCE_COMPENSATION_FAILED` / `SOURCE_RECONCILIATION_REQUIRED` mapping.
10. **Audit category:** every unsafe upload denial emits one structured diagnostic line on `stderr` with stable prefix `security-audit category=unsafe-upload-denial` and safe fields only (correlation id, owner id, reason keyword, allowlisted extension token, byte size). No filename text, body bytes, paths, or credentials. Full persisted Security Audit Events (DEC-214) are future work (Limitations).

Add one additive forward migration (0003) relaxing exactly three check constraints: `sources_source_type_check` → `IN ('pasted_text','uploaded_text')`, `sources_capture_type_check` → `IN ('pasted_text','uploaded_text')`, `source_raw_snapshots_content_type_check` → `IN ('text/plain; charset=utf-8','text/markdown; charset=utf-8')`. ## Acceptance Criteria

1. A valid owner-scoped `.txt` upload and a valid `.md` upload each create one Source Reference (`sourceType=captureType='uploaded_text'`), one immutable Raw Snapshot whose SHA-256 and byte size match the exact original file bytes, and one Normalized Working Copy seeded with the validated decoded text; the snapshot content type reflects the extension.
2. The uploaded Source supports the existing edit → Version → Approval path unchanged; Approval binds one exact eligible Version and is append-only.
3. Role limits apply across capture types: a second Primary (any capture type) and a sixth Supporting Source fail closed with `SOURCE_ROLE_LIMIT_EXCEEDED`.
4. Quarantine denials fail closed with 422 and stable keywords, and create no Object Storage object and no database state: disallowed extension (`.exe`, `.html`, `.md.exe`, missing extension), disallowed declared MIME (`text/html`, `image/png`), invalid UTF-8 byte sequence, file larger than 100,000 bytes, empty or whitespace-only content, NUL byte, disallowed filename (path separator, control char, >255 bytes), missing file part, more than one file, unknown or missing `role`.
5. A BOM-prefixed file captures successfully: the Raw Snapshot preserves the original bytes (BOM included) while the Working Copy text has the BOM stripped; CRLF bytes are preserved exactly in the snapshot.
6. When no label is supplied, the label is derived from the sanitized filename stem; an explicit label still obeys the existing label rules.
7. Oversized multipart payloads rejected by plugin limits still produce the formal 422 error envelope (no connection reset garbage, no partial state).
8. Each unsafe upload denial emits exactly one `security-audit category=unsafe-upload-denial` diagnostic containing only safe fields.
9. Source list/get responses for uploaded Sources validate against the updated response schemas and expose no storage key, credential, or signed URL.
10. Migration 0003 applies cleanly from 0002 on a fresh database; `corepack pnpm db:generate` reports no further schema changes; pre-existing pasted-text rows and constraints for non-allowlisted values behave as before (non-allowlisted `source_type`/`capture_type`/`content_type` still rejected).
11. Missing Session and owner mismatch fail closed as before on the new route.
12. Unit, contract/schema-sync, repository/migration, protected-API integration (multipart happy path + every denial), regression (`check`, `repository:check`, frozen lockfile, audit), and failure-injection gates pass.
13. Documentation reports only what exists: upload capture + quarantine exist; URL Fetcher, Workflow, UI, and M3 remain absent. No governance status text is edited.
